1. INTRODUCTION
Banking is an important part of everyday life. Customers use banks to keep money safely, check account balances, transfer funds and review transactions. Traditional banking often requires customers to visit a branch or depend on separate services to complete simple tasks. A web-based Bank Management System can make basic banking operations easier by providing a single interface for account-related activities.
The Bank Management System is a full-stack web application designed to demonstrate common banking functions. Users can register, log in, view a dashboard, check account details, deposit money, withdraw money and view transaction history. The frontend provides a simple interface, while the backend validates requests and processes transactions. A database stores user, account and transaction records.
This project is intended as an educational prototype. It demonstrates the connection between frontend pages, backend APIs and a database. It is not a production banking platform and should not be used to store real money or sensitive financial information.
2. ABSTRACT
The Bank Management System is a web-based application developed to organise basic banking operations in one place. The proposed application includes user registration and login, dashboard display, deposit, withdrawal, balance enquiry and transaction history. It aims to reduce manual record handling, improve the speed of routine operations and present account information in a clear format.
The frontend can be developed using HTML, CSS and JavaScript. A Node.js and Express backend can receive requests, validate input and apply banking rules. A database such as MySQL can store user profiles, account balances and transaction records. The system follows a client-server model: users interact with web pages, the backend processes the request, and the database stores or retrieves the required information.
The project provides a foundation for learning full-stack development, form validation, API communication, database design and basic security practices. Features such as secure authentication, audit logs, role-based access and stronger transaction controls can be added as the project develops.
3. PROBLEM STATEMENT
Manual or disconnected methods of managing account information can make it difficult to find records quickly, track transactions and maintain consistent data. Repeated data entry can also cause mistakes. A centralised application is needed to demonstrate how account operations can be organised through a user-friendly interface.
* Account information may be scattered across different records or pages.
* Users may not have a convenient way to view recent transactions in one place.
* Manual calculations can lead to balance errors.
* Without validation, incorrect amounts or incomplete form details may be submitted.
* Separating the interface, processing logic and database is necessary for a maintainable application.
4. OBJECTIVES OF THE PROJECT
* To develop a simple and user-friendly web-based banking application.
* To provide registration and login pages for users.
* To display account details and available balance on a dashboard.
* To support deposit and withdrawal operations in the project environment.
* To record each successful operation in transaction history.
* To validate user input and prevent invalid transaction amounts.
* To connect frontend pages with a backend server through APIs.
* To store and retrieve account and transaction information from a database.
* To demonstrate basic authentication, access control and error handling.
5. EXISTING SYSTEM
In a basic manual or disconnected system, account details and transaction records may be maintained through paper documents, spreadsheets or separate applications. Such approaches can be suitable for small demonstrations, but they can become difficult to manage as the number of records increases.
Drawbacks of the Existing System
* Searching for previous transactions can take extra time.
* Repeated manual entry may introduce mistakes.
* Balance calculations require careful checking.
* Records may not be available in one centralised view.
* Input validation and access control may be inconsistent.
* Reports and transaction summaries may require manual preparation.
6. PROPOSED SYSTEM
The proposed Bank Management System brings basic account activities together in a web application. A user registers or logs in and accesses a dashboard. From the dashboard, the user can view account information, make a deposit or withdrawal in the demonstration environment, and review transaction history. The backend checks the request and updates the database only when the operation is valid.
Key Features
* User registration and login.
* Dashboard with account summary and balance.
* Deposit form with amount validation.
* Withdrawal form with sufficient-balance validation.
* Transaction history showing type, amount, date and status.
* Clear success and error messages.
* Centralised database storage for user, account and transaction records.

8. SYSTEM ARCHITECTURE
The application follows a three-layer client-server architecture.
1. Presentation Layer: HTML, CSS and JavaScript pages display forms, buttons, account summaries and transaction history.
2. Application Layer: Node.js and Express receive requests, validate input, verify permissions and apply deposit or withdrawal rules.
3. Data Layer: The database stores user records, account balances and transaction history.
USER / WEB BROWSER
↓
FRONTEND: HTML + CSS + JavaScript
↓  HTTP requests / API responses
BACKEND: Node.js + Express
↓  Database queries
DATABASE: MySQL
For a deposit or withdrawal, the backend should perform validation and update the balance and transaction record as one database transaction. This helps avoid inconsistent records if an operation fails partway through.

FRONTEND DEVELOPMENT
The frontend is the part of the application visible to the user. Each page should have clear navigation and consistent styling. HTML defines the page structure, CSS styles the components, and JavaScript handles interactions and communicates with the backend.
Main Pages
* index.html - home page with a short introduction and navigation.
* login.html - form for entering login credentials.
* register.html - form for creating a user account.
* dashboard.html - summary of account information and available actions.
* deposit.html - form to enter a deposit amount.
* withdraw.html - form to enter a withdrawal amount.
* style.css - shared styles for the pages.
* script.js - common frontend behaviour and API communication.
The frontend should show clear validation messages, disable repeated submissions while a request is processing, and never treat a client-side balance as authoritative. The backend must always verify the balance and amount before saving a transaction.
11. BACKEND DEVELOPMENT
The backend receives requests from the frontend and performs the main application logic. Express routes can be created for registration, login, account details, deposits, withdrawals and transaction history. Each route should validate the request, check that the current user is authorised, interact with the database and return a suitable response.
Example API Endpoints
EndpointPurposePOST /api/registerCreate a user account after validating the submitted details.POST /api/loginVerify credentials and start an authenticated session.GET /api/accountReturn the authenticated user's account summary.POST /api/depositValidate and record a deposit.POST /api/withdrawValidate available balance and record a withdrawal.GET /api/transactionsReturn the user's transaction history.The backend should use parameterised database queries, handle errors safely and keep secrets such as database passwords in environment variables rather than directly in source code.
12. DATABASE MANAGEMENT
A relational database can store information in related tables. A simple design may include Users, Accounts and Transactions. Each account should have a unique identifier, and every transaction should reference the account affected by the operation.
Suggested Tables
TableExample FieldsUsersuser_id (primary key), full_name, email (unique), password_hash, created_atAccountsaccount_id (primary key), user_id (foreign key), account_number (unique), balance, created_atTransactionstransaction_id (primary key), account_id (foreign key), transaction_type, amount, transaction_date, status, descriptionPasswords must be stored as secure password hashes, not plain text. The balance should be updated only by the backend. Deposit and withdrawal updates should be recorded together with their transaction entry so that the account balance and history remain consistent.
13. MAIN MODULES
13.1 User Registration and Login
The registration module collects the required user details and checks that fields are complete and valid. Login verifies the submitted credentials and grants access only after successful authentication. Passwords should be hashed using a suitable password-hashing library.
13.2 Dashboard
The dashboard provides a summary of the account, current balance and navigation to deposit, withdrawal and transaction history pages. Account data must be loaded from the backend for the authenticated user.
13.3 Deposit
The deposit module accepts a positive numeric amount. The backend validates the amount, updates the account balance and creates a transaction record. A success message is displayed only after the database operation succeeds.
13.4 Withdrawal
The withdrawal module accepts a positive amount and checks that the account has enough available funds. If the amount is invalid or the balance is insufficient, the request is rejected and the balance remains unchanged.
13.5 Transaction History
This module lists previous deposits and withdrawals with the transaction type, amount, date and status. Users should only be able to view transactions belonging to their own account.

15. SECURITY FEATURES
* Use HTTPS when deployed on a server.
* Hash passwords using a recognised password-hashing algorithm.
* Use server-side validation for every important field.
* Use parameterised SQL queries to reduce SQL injection risk.
* Protect private routes with authentication and authorisation checks.
* Do not expose database credentials, secret keys or sensitive error details.
* Use database transactions for balance changes and transaction logging.
* Maintain audit logs for important actions and apply rate limits to login attempts.
* Use only fictional data for a student demonstration; never enter real banking credentials or real customer financial details.

20. CONCLUSION

The system includes user registration and login, a dashboard, deposit and withdrawal operations, and transaction history. HTML, CSS and JavaScript provide the user interface, Node.js and Express handle application logic, and a relational database stores the records.
